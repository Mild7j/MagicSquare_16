## 문서 목적

본 보고서는 4×4 합 일치 격자(Magic Square) 프로그램을 만들기 **이전**에 수행한 **문제 인식 및 문제 정의** 단계의 결과를 정리한 것이다. 구현 설계, 코드, 알고리즘은 범위에 포함하지 않는다.

---

## STEP 1 — Observation (관찰)

### 1.1 현재 우리가 해결하려는 상황은 무엇인가?

**관찰:** QA 전문가가, 아직 내용이 비어 있는 개발 공간에서, **4×4 격자에 1~16을 한 번씩 배치했을 때** 행·열·대각선 합이 모두 같아지는지를 다루는 **작은 소프트웨어 대상**을 정의하려고 한다.

이는 “숫자 퍼즐 하나를 풀자”라기보다 다음에 가깝다.

- **요구가 아직 문장·예시·실패 사례로 고정되지 않은 초기 단계** — 무엇을 입력·출력·검증할지, 사람이 쓰는지 자동으로 돌리는지, “맞는 배치 하나”인지 “모든 경우”인지가 열려 있음
- **QA 관점의 출발점** — 나중에 “이게 맞다/틀리다”를 말할 **기준(oracle)** 과 **관찰 가능한 증거(출력, 로그, 상태)** 가 아직 관찰 단계에서 정리되지 않음
- **이름만 있는 저장소** — `MagicSquare_xx`는 의도는 보이지만, 관찰 가능한 산출물(명세, 샘플, 테스트 데이터)은 아직 없음

**요약:** “4×4 합 일치 격자”라는 수학적 대상을, **검증 가능한 프로그램 과제로 바꾸기 전의 문제 인식 구간**이다.

### 1.2 왜 4×4 마방진 문제를 다루는가?

4×4는 “작지만 비어 있지 않은” 경계에 있다.

| 관찰 포인트 | 4×4에서 드러나는 것 |
|------------|-------------------|
| 규모 | 3×3보다 **규칙·예외·대칭**이 많고, 손으로 전부 나열하기는 부담됨 |
| 수학 | 합이 **34**로 고정되는 등 **단일 기준값**으로 판정하기 쉬움 |
| QA | 입력·출력·불변식 검증이 **명확한 oracle** 로 쓰이기 좋음 |
| 설계 | UI·CLI·API·배치 등 **여러 형태**로 같은 핵심 로직을 둘 수 있음 |
| 학습 | 알고리즘·상태 공간·조합 폭발을 **코드 없이도** 먼저 말로 정리할 수 있음 |

QA 전문가 입장에서는 **판정 기준이 분명하고, 경계값·오류 입력·부분 결과를 설계할 수 있는 연습 대상**으로 4×4가 자주 선택된다.

### 1.3 이 문제는 어떤 학습 또는 시스템 설계 맥락에서 등장하는가?

**학습 맥락**

- 알고리즘·자료구조: 백트래킹, 순열/조합, 제약 만족
- 수학·논리: 불변식(합=34), 대칭·회전·반사 등 동치 클래스
- 소프트웨어 공학 입문: 요구 → 모듈 경계 → 단위/통합 테스트
- QA·테스트: 동등 분할, 경계값, oracle 설계, 회귀·속성 기반 테스트

**시스템·제품 맥락**

- 단일 기능 유틸: 격자 입력 → 합 일치 여부 판정
- 생성·탐색 서비스: 조건을 만족하는 배치 탐색 또는 개수 반환
- 교육/게임: 힌트, 단계, 점수 — 도메인 규칙이 수학 규칙보다 커짐
- 라이브러리/API: 외부 시스템이 “유효한 4×4 배치인지”를 위임

**QA·품질 맥락**

- 요구 모호 시 관찰 질문: 빈 칸 허용?, 중복 숫자?, 하나만 찾으면 되는지 전부인지, 회전·대칭 동치 처리
- 실패의 관찰 가능성: 잘못된 합, 누락 숫자, 범위 밖 값
- 비기능: 4×4는 작아 성능 이슈는 거의 없으나 **명확성·재현성·문서화**가 품질의 중심

### 1.4 관찰 관점 한 줄 요약

지금의 상황은 **“4×4에서 1~16을 격자에 놓았을 때 여러 방향의 합이 같다는 조건을, 아직 정의되지 않은 프로그램이 사람·테스트·다른 시스템 앞에서 어떻게 드러내고 판정할 것인가”** 를 QA·학습·설계 관점에서 **먼저 바라보는 단계**이다.

## STEP 2 — Why #1

**질문:** 왜 마방진을 완성해야 하는가?

### 2.1 가정한 답 (A)

> **“4×4 격자에 1~16을 한 번씩 배치해, 모든 행·열·대각선의 합이 34가 되는 ‘완성된 배치’를 얻어야, 그 결과가 요구(과제·명세·데모)를 충족했는지 증명할 수 있기 때문이다.”**

완성은 목적 자체가 아니라 **“요구를 만족했다는 관찰 가능한 산출물”** 을 확보하기 위한 수단이다.

### 2.2 A에서 드러나는 불편함 · 구조적 문제

#### (1) 목적이 “완성”에 고정되어 있음

- A는 **최종 격자 한 장**만 성공으로 본다 → “거의 맞음”, “한 줄만 틀림”, “왜 불가능한지”는 실패 산출물로 취급되지 않음
- 완성 = 증명 → **검증·탐색·생성·설명**이 한 목표에 묶임

**불편함:** QA 입장에서 “완성 못 함”도 중요한 정보인데, **이진 성공(완성 vs 미완성)** 으로 세계를 자른다.

#### (2) “완성해야 한다”가 누구·언제를 숨김

- 행위 주체(학습자, 사용자, 자동 프로그램)가 없음
- “증명”의 대상(교수, 리뷰어, CI, 본인)이 없음

**불편함:** “누구에게 완성을 보여야 하나?” 가 비어 있어 요구·테스트 범위가 흔들린다.

#### (3) “완성”이 하나의 해를 전제함

- 4×4는 **서로 다른 완성 배치가 여러 개** 존재
- “그 격자” = 정답 vs **어느 해를 기대하는지**, **회전·반사 동치** 미정

**불편함:** oracle이 **“합=34인가?”** 인지 **“이 특정 배치인가?”** 인지 A만으로는 정해지지 않는다.

#### (4) 증명 수단이 결과만을 가리킴

- A의 증거 = 완성된 4×4 → 과정·시도 규칙은 품질 범위 밖
- 합 34만 보면 **1~16 각 1회** 등 다른 결함은 별도 검사 필요

**불편함:** “우연히 맞춘 표”와 “규칙을 지킨 표”를 구분할 수 없다.

#### (5) “완성해야 한다”가 반드시 가능하다고 가정

- 잘못된 부분 입력·불가능한 제약이면 **완성 자체가 요구 불능**
- “완성 불가 + 이유”가 A의 성공 정의에 없음

**불편함:** “완성하라”는 지시가 **모순**이 될 수 있다.

#### (6) QA 관점: 테스트 가능성과 목적의 어긋남

- A는 **산출물 중심** → QA는 **행위·경계·오류 메시지·재현**까지 품질 범위
- “완성 = 통과” → 부분 검증, 속성, 회귀 등 테스트 전략이 A에 없음

### 2.3 구조 요약

가정한 A는 **“완성된 격자 = 요구 충족의 유일한 증거”** 로 읽힌다. 불편함은 “완성이 어렵다”가 아니라, **“완성”이라는 말 하나에 서로 다른 요구(생성·검증·탐색·교육·데모)가 겹쳐 붙는 구조**에서 온다.

### 2.4 후속 관찰 질문

1. 완성의 정의: 합만 34인가, 특정 패턴/규칙을 따랐는가?
2. 완성의 개수: 하나면 충분한가, 전부 나열해야 하는가?
3. 완성 실패 시: 무엇을 사용자·테스트가 **관찰**해야 하는가?

## STEP 3 — Why #2

**질문:** 왜 단순 계산이 아니라 프로그램으로 구현하는가?

### 3.1 반복 가능성 (Repeatability)

**답:** 같은 조건·같은 입력에 대해, **언제·누가 실행해도 동일한 절차와 결과**를 얻기 위해서이다.

| 손 계산·수기 | 프로그램 |
|-------------|----------|
| 피로·주의력에 따라 검사 순서·누락이 달라짐 | 동일 입력 → 동일 출력(결정적 로직일 때) |
| “어제는 맞았는데 오늘은 한 칸을 놓침” | 실행 기록·버전·입력으로 **재현** 가능 |
| 해를 하나 찾으면 그만둠 | N번 실행, 여러 케이스로 **반복 실험** 가능 |

**구조적 이슈:** “반복 가능”하려면 **입력 형식·실행 환경·버전**이 문서화되어야 한다.

### 3.2 검증 자동화 (Verification Automation)

**답:** “이 배치가 규칙을 만족하는가?”를 **사람의 눈과 머리 계산 대신, 기계가 oracle로 판정**하게 하기 위해서이다.

| 검증 항목 | 손 검증 | 자동 검증 |
|----------|---------|-----------|
| 1~16 각 1회 | 눈으로 중복·누락 | 집합·카운트 |
| 행·열·대각 합 = 34 | 계산 실수·순서 누락 | 체계적 전수 검사 |
| 여러 후보 비교 | 표 여러 장 관리 어려움 | 배치·테스트 스위트 |

**구조적 이슈:** **무엇을 검증할지**가 분명해야 한다. 잘못된 oracle을 빠르게 반복할 위험이 있다.

### 3.3 오류 방지 (Error Prevention)

**답:** 산술·누락·일관성 붕괴를 줄이고, 실패를 **빨리·일관되게 발견**하기 위해서이다.

**손 작업에서 흔한 오류:** 부분만 맞는 착시, 15 두 번·7 누락, 대각선 검사 누락, 회전·대칭 해를 틀림으로 오인.

**구조적 이슈:** 프로그램은 **논리 버그·경계값 누락**이라는 새 오류 층을 만든다.

### 3.4 규칙 기반 사고 훈련 (Rule-based Thinking Training)

**답:** “감으로 채우기”가 아니라 **명시적 규칙·불변식·제약**으로 문제를 다루는 연습을 하기 위해서이다.

명시되어야 하는 것: magic sum = 34, 1~16 각 1회, 행·열·대각 검사 범위, 입출력·실패 시 관찰 내용.

**구조적 이슈:** 말로 애매했던 것(동치, “아무 해 하나”, 부분 채움)이 **구현·테스트에서 강제로 결정**된다.

### 3.5 네 관점 통합

| 관점 | 프로그램을 쓰는 이유 | 단순 계산만으로 남는 갭 |
|------|---------------------|-------------------------|
| 반복 가능성 | 같은 판정·실험을 N번 | 재현 조건이 사람마다 다름 |
| 검증 자동화 | oracle을 기계에 고정 | 느리고, 누락되고, 회귀 어려움 |
| 오류 방지 | 체계적·전수 검사 | 부분 성공 착시, 산술·중복 실수 |
| 규칙 기반 사고 | 규칙을 명시·실행 가능하게 | 암묵지·모호한 “맞다” |

**STEP 2와의 연결:** STEP 2는 **산출물(완성 격자)** 중심, STEP 3은 **과정·판정·재현을 기계에 맡기자**는 동기. 다음 질문: **프로그램의 역할이 ‘완성’인가 ‘검증’인가 ‘둘 다’인가?**

## STEP 4 — Why #3 (핵심 발견)

**질문:** 왜 이 문제를 TDD 방식으로 설계하려 하는가?

### 4.1 핵심 발견 (요약)

4×4 합 일치 격자 문제는 **규칙이 분명하고 oracle이 수학적으로 정해져 있어**, 요구를 **실패하는 예시 → 통과하는 예시**로 고정하기에 적합하다. TDD는 구현 습관이 아니라 **“무엇이 맞는지 통제하고, 무엇이 변하면 안 되는지 드러내는 설계 순서”** 이다.

### 4.2 무엇이 통제되어야 하는가?

| 통제 대상 | 내용 |
|----------|------|
| 판정 기준 (oracle) | 합만 / 숫자 집합 / 특정 해 |
| 범위 | 생성·검증·탐색·UI 분리 |
| 회귀 | 리팩터 후에도 같은 입력·같은 기대값 |
| 모호한 요구 | 관찰 가능한 계약으로 전환 |
| 구현 세부 | API·입출력·불변식에 테스트를 묶음 |

**통제의 중심은 “코드 구조”가 아니라 “무엇을 맞다고 볼 것인가”** 이다.

### 4.3 어떤 불변 조건이 존재하는가?

**도메인 불변식 (A)**

| ID | 내용 |
|----|------|
| Magic sum | n=4일 때 목표 합 = **34** |
| 숫자 집합 | {1,…,16} 각 **정확히 1회** |
| 행·열·대각 | 각각 합 = 34 (총 10개 선분) |

**시스템·QA 불변 (B)**

| ID | 내용 |
|----|------|
| 결정성 | 같은 입력 → 같은 판정·출력 |
| 단조적 거부 | 위반 입력은 통과로 바뀌지 않음 |
| 검증 완전성 | 정의된 전체 검사 항목을 다 봄 |

**정책으로 정할 것 (C)** — 수학 필수 아님

- 회전·반사 동치
- 아무 유효 해 하나 vs 특정 해 vs 전체 나열
- 빈 칸·부분 격자 허용
- 생성과 검증의 모듈 분리

### 4.4 왜 입력/출력이 명확해야 하는가?

**입력:** 실험 재현, 경계값(빈 칸, 중복, 범위 밖), 역할 분리(검증 vs 생성), 실패 유형 분류.

**출력:** oracle 표현(통과/거부만 vs 진단), QA 관찰 가능성, 다중 해 처리 방식, 디버깅·교육 가치.

**핵심:** I/O가 모호하면 TDD는 **구현을 이끌지 못하고**, 구현이 테스트를 **사후 합리화**한다.

### 4.5 STEP 2~4 tension 정리

| 단계 | 초점 |
|------|------|
| STEP 2 | 완성 = 유일한 증거 → 부분 실패·불가능 입력 가려짐 |
| STEP 3 | 반복·자동 판정·오류 감소 |
| STEP 4 | 테스트로 불변식·계약을 구현 전에 고정 |

## STEP 5 — 진짜 문제 정의

### 5.1 표면 문제 정의 (잘못된 정의)

> **「4×4 마방진을 완성하는 프로그램을 만든다.」**

| 오해 | 문제점 |
|------|--------|
| 목표가 완성된 격자 한 장뿐 | 검증·거부·부분 입력·불가능 상황 누락 |
| “맞다”의 기준이 모호 | 합만 / 집합 / 특정 배치 불명확 |
| 누가·무엇을 위해 하는지 없음 | 학습·QA·데모·도구가 뭉개짐 |
| 실패 = 미완성 | 틀린 격자·잘못된 입력·진단이 관찰 대상 아님 |
| 프로그램 = 답을 찾는 장치 | 반복 판정·회귀·명세 고정 빠짐 |

**본질:** 수학 퍼즐 **결과물**만 제품으로 삼고, **계약·불변식·관찰 가능한 판정**은 정의하지 않는다.

### 5.2 개선된 문제 정의 (정확한 정의)

> **「4×4 격자에 1부터 16까지의 정수가 각각 한 번씩 배치된 경우를 입력으로 받아, 행·열·두 대각선의 합이 모두 34인지를 일관되게 판정하고, 그 판정 결과를 반복 가능한 방식으로 관찰할 수 있게 한다. 필요 시, 주어진 규칙을 만족하는 배치를 산출하되, 산출물도 동일한 판정 기준을 통과해야 한다.」**

| 요소 | 내용 |
|------|------|
| 대상 | 4×4, 1~16, 각 1회 |
| 핵심 행위 | **판정** (필수); **산출** (선택, 범위 명시) |
| 성공 | 불변식 만족 → 통과로 관찰 |
| 실패 | 불변식 위반·입력 규칙 밖 → 거부, (선택) 깨진 조건 구분 |
| 품질 | 결정성, 판정 기준 문서화·재현 |
| 범위 밖(명시 필요) | UI, 게임 규칙, 대칭 동치, 전체 해 나열 |

**본질:** “퍼즐을 푼다”가 아니라 **합 일치 배치 도메인 규칙을 관찰 가능한 판정과(선택) 산출로 다루는 시스템**을 정의한다.

### 5.3 핵심 Invariant

#### 도메인 불변식 (필수)

| ID | 불변 조건 |
|----|----------|
| **I1** | 네 행, 네 열, 주대각·부대각 — **10개 선분** 합 = **34** |
| **I2** | 16칸 값 집합 = **{1, 2, …, 16}** (중복·누락·범위 밖 없음) |
| **I3** | **4×4**, 모든 칸 유효 정수 (부분 채움·빈 칸은 별도 정책) |

#### 시스템·품질 불변식

| ID | 불변 조건 |
|----|----------|
| **S1** | 동일 입력 → 통과/거부 불변 |
| **S2** | 검증 시 I1·I2·I3 **빠짐없이** 적용 |
| **S3** | 산출 격자는 I1·I2·I3 만족 |
| **S4** | 위반 입력·산출물은 통과로 표시되지 않음 |

#### 정책 (문서화 필요)

| ID | 질문 |
|----|------|
| **P1** | 회전·반사 동치 처리 |
| **P2** | 유효 배치 하나 vs 전부 |
| **P3** | 검증만 vs 산출 포함 |
| **P4** | 통과/거부만 vs 진단 정보 |

### 5.4 훈련하려는 사고 능력

| # | 사고 능력 | 연습 내용 |
|---|----------|----------|
| T1 | 요구 분리 | 완성 / 판정 / 산출 역할 분리 |
| T2 | 불변식 사고 | I1~I3을 먼저 고정 |
| T3 | Oracle 설계 | 통과/거부를 검사 항목으로 정의 |
| T4 | 입출력 계약 | 실험 가능한 자극·관측 기술 |
| T5 | 경계·실패 분류 | 부분 맞음·집합 위반·형식 오류 구분 |
| T6 | 반복 가능한 품질 | 같은 기준 N번 적용·회귀 |
| T7 | 범위 통제 | P1~P4 미결정 항목 명시 |
| T8 | TDD적 설계 순서 | “무엇이 먼저 실패해야 하는가”를 불변식으로 표현 |

**한 줄 요약:** “4×4 마방진 공식”이 아니라, **요구를 판정 가능한 불변식과 관찰 가능한 계약으로 바꾸는 QA·규칙 기반 사고**를 훈련한다.

### 5.5 표면 vs 개선 대조

| 구분 | 표면 정의 | 개선 정의 |
|------|----------|----------|
| 중심 | 완성된 격자 | 규칙에 대한 **판정** (+ 선택적 산출) |
| 성공 | 답 한 장 | 불변식 충족 **관찰** |
| 실패 | 미완성 | 명시적 **거부**·(선택) 진단 |
| 증거 | 결과물만 | 재현 가능한 **판정·기록** |
| 훈련 | 퍼즐 풀이 | 요구·불변식·계약·품질 사고 |
