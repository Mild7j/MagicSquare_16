# MagicSquare_xx

4×4 **합 일치 격자**(Magic Square)를 다루는 프로그램 프로젝트입니다.  
1부터 16까지의 정수를 4×4 격자에 한 번씩 배치했을 때, 모든 행·열·대각선의 합이 **34**가 되는지를 **판정**하고, 필요 시 유효한 배치를 **산출**하는 것을 목표로 합니다.

현재 단계는 **구현 이전의 문제 정의**입니다. 요구·불변식·QA 관점을 먼저 고정한 뒤, TDD 방식으로 개발을 진행할 예정입니다.

---

## 프로젝트 배경

| 관점 | 요약 |
|------|------|
| **대상** | 4×4 격자, 값 1~16, magic sum = 34 |
| **주요 독자** | QA 전문가, 요구·테스트 설계를 연습하는 개발자 |
| **접근** | 문제 인식(STEP 1~5) → (예정) TDD 기반 구현 |
| **품질 초점** | 반복 가능한 판정, 자동 검증, 명확한 입·출력 계약 |

4×4는 규모가 작아 **oracle(판정 기준)** 이 분명하면서도, 손 계산만으로는 반복·회귀·전수 검사가 부담되는 **QA·규칙 기반 사고**에 적합한 연습 도메인입니다.

---

## 문제 정의 (요약)

### 피해야 할 표현 (표면 정의)

> 「4×4 마방진을 완성하는 프로그램을 만든다.」

완성된 격자 한 장만을 목표로 삼으면, **검증·거부·부분 실패·불가능 입력**이 요구에서 빠지기 쉽습니다.

### 채택한 정의 (개선 정의)

> **4×4 격자에 1~16이 각각 한 번씩 배치된 경우를 입력으로 받아, 행·열·두 대각선의 합이 모두 34인지를 일관되게 판정하고, 그 결과를 반복 가능하게 관찰할 수 있게 한다. 필요 시 규칙을 만족하는 배치를 산출하되, 산출물도 동일한 판정 기준을 통과해야 한다.**

| 요소 | 내용 |
|------|------|
| **핵심 행위** | 판정 (필수) · 산출 (선택, 범위 명시) |
| **성공** | 도메인 불변식(I1~I3) 충족 → 통과로 관찰 |
| **실패** | 불변식 위반 또는 입력 규칙 밖 → 거부 (선택: 깨진 조건 구분) |
| **품질** | 결정성, 판정 기준 문서화, 재현 가능성 |

상세 논의는 [Report/Problem-Definition-Report.md](./Report/Problem-Definition-Report.md)를 참고하세요.

## 핵심 Invariant

### 도메인 (필수)

| ID | 조건 |
|----|------|
| **I1** | 4행, 4열, 주대각·부대각 — **10개 선분**의 합 = **34** |
| **I2** | 16칸 값의 집합 = **{1, 2, …, 16}** (중복·누락·범위 밖 없음) |
| **I3** | **4×4** 격자, 모든 칸이 유효한 정수로 채워짐 |

### 시스템·품질

| ID | 조건 |
|----|------|
| **S1** | 동일 입력 → 동일 통과/거부 |
| **S2** | 검증 시 I1·I2·I3을 빠짐없이 적용 |
| **S3** | 산출된 격자는 I1·I2·I3을 만족 |
| **S4** | 위반 입력·산출물은 통과로 표시되지 않음 |

### 정책 (구현 전 결정 예정)

| ID | 결정 사항 |
|----|----------|
| **P1** | 회전·반사를 같은 해로 볼지 |
| **P2** | 유효 배치 하나 vs 전체 |
| **P3** | 검증만 vs 산출 포함 |
| **P4** | 통과/거부만 vs 진단 정보 제공 |

## 왜 이 프로젝트인가

문제 정의 단계(STEP 1~5)에서 정리한 동기입니다.

1. **관찰 (STEP 1)** — “퍼즐을 푼다”가 아니라, **규칙을 프로그램·테스트 앞에서 어떻게 드러내고 판정할지**를 먼저 정의
2. **Why #1 (STEP 2)** — “완성 = 증거”만으로는 QA에 필요한 **실패·부분 맞음·다중 해**가 가려짐
3. **Why #2 (STEP 3)** — 반복 가능성, 검증 자동화, 오류 방지, 규칙 기반 사고를 위해 **프로그램**이 필요
4. **Why #3 (STEP 4)** — TDD로 **판정 기준·불변식·입출력 계약**을 구현 전에 통제
5. **진짜 문제 (STEP 5)** — 표면 정의를 버리고 **판정 중심** 정의와 Invariant로 고정

요구 분리 · 불변식 사고 · Oracle 설계 · 입출력 계약 · 경계·실패 분류 · 반복 가능한 품질 · 범위 통제 · TDD적 설계 순서
